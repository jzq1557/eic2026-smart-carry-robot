## 0. 这套东西是什么

一台「智能搬运」小车，上下位机分工：

| | 硬件 | 负责 |
|---|---|---|
| **上位机** | RDK X5（Ubuntu，root） | 视觉瞄准、底盘路线、动作编排、界面推流 |
| **下位机** | STM32F103ZET6 | 定时器脉冲、斜坡加减速、Emm_V5 闭环电机、舵机 |

机械构成（2026-09-16 车主确认，别再按"老师那台"想当然）：

- **伸缩滑台** = TTL 闭环 **id1**（`0x10`）
- **龙门架升降** = TTL 闭环 **id2 + id3 两台电机反向传动**（`0x11`，内部自动 id2=dir、id3=反向）
- **base 轴** = TTL 闭环 **id4**（`0x12`）
- **夹爪** = **舵机**（`0x14` 开关 / `0x15` 任意角度），**不是** TTL 脉冲

通信：USB-TTL `/dev/ttyUSB0` ↔ STM32，**115200-8N1**。
协议：`0xFF + cmd + 7B payload + 0xFE`，共 10 字节，无校验，大端。

## 2. 本轮（2026-09-18）改了什么

### 2.1 `place_demo.py`：工序顺序纠正 ★

**旧（错）**：`回作业位 → 夹料 → 瞄准 → 放置` —— 瞄准算出来的偏移**根本没被用上**。
**新（对）**：`回作业位 → 瞄准 → 归零 → 去物架夹料 → 回放到靶心 → 放置 → 回零`

与 `aim.py` 里现场验证过的 `place_mission()` 同构：
`converge → replay(off,-1) → BUILTIN_GRAB_VEH → replay(off,+1) → BUILTIN_PLACE`

新增两个按键（对应那两次 replay）：
- `z` 归零 = `car.replay(off, -1)` → 回到夹料的**确定起点**
- `b` 回放 = `car.replay(off, +1)` → 回到刚瞄好的**靶心**
带状态机（`none/aimed/zeroed/backed`），重复按会被拦下。

**为什么必须归零**：瞄准会用**伸缩**修画面 y（offset 常有几百脉冲），而动作组里的
`arm_in` 是**相对**位移 → 不归零的话每次落点都不一样，可能撞物架。

### 2.2 `place_demo.py`：自带一份动作参数

原来 `from grab_demo import RACK_LIFT_UP, ARM_IN_VEL, BASE_90 …` = **两边共用同一个变量**，
在 grab_demo 里改一个值 place_demo 偷偷跟着变。
现在 place_demo 参数区自带完整一份（含 `_deg2pulses()`），四个辅助函数全部**显式传参**，
`import` 只剩函数。菜单 `p` 可打印这份备份对照。

### 2.3 grab / place 嵌入跑图 ★

- `s3_material`（原料区）：每个料位 `瞄准 → 取料 → 归零 → 放到对应颜色置物架`
- `s6_process`（加工区）：每个靶位 `run_one()` = `瞄准 → 归零 → 取料 → 回靶心 → 放置 → 回零`
- 两处都用**函数内 import**（`place_demo → grab_demo → route_main` 会成环）

**"放完回零"为什么必须做**：瞄准动过**伸缩**（相对位移）。下一个靶位开头会把
**base** 用 `goto_base_deg(90°)` 拉回来，但**伸缩没人纠正** → 每个靶位伸缩起点都不同。

### 2.4 TTL 单轴估时：补加减速段 + 按轴裕量 ★

**现场现象**："伸缩台/龙门还没到位，下一步动作就开始了"。

**根因链**：
1. 固件 `TTLctrl.c`：`0x10/0x11/0x12` 是**非阻塞**的（"发完即返回,不等待"）→ 上位机只能按时间估；
2. 固件 `car_config.h`：`TTLCTRL_ACC_DEFAULT = 60`（非 0 → **带加减速**）；
3. 老公式 `脉冲×60/(RPM×3200)` **只算匀速段**，漏了加速段和减速段。

误差随速度放大（6500 脉冲伸缩）：

| 速度 | 匀速 | 加减速 | 真实 | 老公式只等 | 结果 |
|---|---|---|---|---|---|
| 40 RPM | 3.05s | ~0.27s | ~3.3s | 3.30s | ✅ 看不出 |
| **200 RPM** | **0.61s** | **~1.33s** | **~1.9s** | **0.86s** | ❌ 少等 1.3 秒 |

**修法**：
- `car.py` 新增 `ttl_time()` / `ttl_wait()` / `ttl_extra()`
- `school_config.py` 新增 `TTL_ACC_RPM_PER_S=300`、`TTL_TIME_EXTRA_S=0.25`、
  **`TTL_EXTRA_S={"arm":0,"gantry":0.6,"base":0}`**（龙门是重负载，低转速下加减速比公式慢）
- `route_car.py` 的 `_wait_axis` 改走同一套（它原来也复制了老公式）
- 每次动作打印分解：`等到位 ≈ 1.55s（匀速 0.50 + 加减速 0.20 + 轴裕量 0.60 + 余量 0.25）`

### 2.7 提速（2026-09-18 晚，车主："提高整体运行速度，先从动作组开刀"）

#### (1) 瞄准：四层限幅 → 按误差加权 ★

`aim.py` 的步长被**四层**依次削：`分段限幅` → `AIM_OUT_MAX_PX` → `近中心软化` → `翻转阻尼`，
再叠 `arm 轴额外缩放`。最坏情况一步只走 **0.2px**，看起来就是"每次只修一点点"。

**顺带抓到一个真 bug**：`AIM_LIMIT_STAGES` **不在 `AIM_KEYS` 里** →
在参数区改分段限幅**根本不生效**（一直用 `school_config.py` 那份，`k` 查看时数字还骗人）。

| 参数 | 原 | 现 |
|---|---|---|
| `AIM_LIMIT_STAGES` | `[(60,45),(25,20)]` | **`[(50, 9999), (28,34), (16,19), (10,11)]`** ← >50px **全额** |
| `AIM_OUT_MAX_PX` | 12 | **9**（只当最小档） |
| `AIM_SOFT_ZONE_PX` / `GAIN` | 20 / 0.5 | **10 / 0.7** |
| `AIM_ARM_LIMIT_SCALE` | 0.5 | **0.8** |
| `AIM_DAMP_MAX_FLIP` | 4（1/16） | **2（1/4）** |
| `AIM_DAMP_MAX_FLIP_ARM` | 5（1/32） | **3（1/8）** |
| `AIM_SETTLE_S` | 0.8 | **0.5** |

板下实测（按控制律离线算）：**200px → 5 拍变 1 拍、120px → 4 拍变 1 拍、40px → 2 拍变 1 拍**；
一次瞄准 **~16s → ~5s**。

**预热也一起简化了**（车主："能不能简化一下这个过程，用时太长了"）：

原判据 `stale==0 且 帧间抖动 ≤3px`，而**抖动至少要两帧才算得出来** →
画面再稳，预热也**至少跑 2 帧** = 2×(0.5s settle + 取帧) ≈ **1.2s**。

现在把"抖动"降级为**可选**（新参数 `AIM_WARMUP_JITTER_PX`，默认 `0` = 不检查）：
**只看 `stale == 0`（本帧真检测到）→ 第 1 帧就放行** ≈ **0.6s**，省一半。

敢去掉抖动的理由：真正治"方向反"的是 `stale` 判据（挡住"拿上一轮中心顶替"）；
抖动那条顺带挡的两件事都有兜底 —— "机械余振"由预热前那一次 `AIM_SETTLE_S` 等待负责，
"EMA 还没爬到新位置"只会让**第一拍走得少一点**（第二拍就纠正），**不会让方向反**。
想恢复严格行为把 `AIM_WARMUP_JITTER_PX` 填 `3` 即可。

| 参数 | 现值 | 说明 |
|---|---|---|
| `AIM_WARMUP_FRAMES` | 3 | **上限**（首帧没检测到才继续等），正常只走 1 帧 |
| `AIM_WARMUP_JITTER_PX` | **0.0** | 0 = 不检查抖动；填 3 = 恢复老行为 |
| `AIM_WARMUP_SETTLE_S` | **None** | None = 用 `AIM_SETTLE_S`(0.5)；填 0.25 可再省 0.25s |

> 注：代码里本来就有"按**距离**加权 K"（`_k_scaled`，用目标半径当距离），
> 但现在**关着**（`K_R_SCALE=False`）—— 那个半径是"红色区域等效半径"，把同心圆环也算进去了，
> 随曝光/阈值变，两次标定甚至 `r 变大 K 反而变小`，用它等于引入误差。
> 现在生效的是"按**误差大小**加权"，不依赖任何标定。要恢复按距离加权，
> 得先换个可靠的距离量（**外接框宽度**比面积等效半径稳）。

#### (2) 三轴并行：归零 + 抬升合成一组 ★

`car.py` 新增 `fire_axis()`（只发不等）+ `apply_parallel()`（全部发出后**只等最慢的一步**），
`apply_step` 支持 `("par", [子步…])`。

`place_demo.do_pick_from_rack` 把动作组**第①步（龙门抬升）＋ base 回正 ＋ 伸缩回正**
合成一个并行组 —— 原来 `rack_zero()` 要串行等 base 一段、伸缩一段，然后才抬龙门：

```
★把「归零」并进第①步：龙门抬升 + base 回正(-178) + 伸缩回正(-212) 三轴并行
→ [并行] 龙门架 反转 2800 脉冲 @40RPM（先发不等）
→ [并行] base 正转 178 脉冲 @40RPM（先发不等）
→ [并行] 伸缩 正转 212 脉冲 @40RPM（先发不等）
[并行] 各轴已同时启动 → 等最慢的一步 2.43s
→ 第2步 转到 1 号位：base 87° → 35°      ← base"大回转"在并行组之后 ✓
```

**3.7s → 2.43s**（每次取料省 1.3s，跑图共 6 次取料 → 约 8s）。

**能这么干的原因**：固件 `0x10/0x11/0x12` 本来就是**非阻塞**的（发完即返回），
三个轴各由自己的驱动器执行 → 天生可以同时动，不是我们伪造的并行。
⚠️ 只用于**不同轴**；同轴写两个动作会互相覆盖目标，`apply_parallel` 会打告警。
⚠️ `_run_rack` 的脉冲自检原会误把 `par` 的子步列表当成"非法脉冲"而**跳过整步** —— 已排除。

#### (3) 取消"回 1 号位"的回头路 ★

原来原料区/加工区跑完三个位置都要**绕回 1 号位**再按固定距离出区。
现在**就地停下**，把补偿放到**出区那一段**：

```python
# s4_leave_material
fwd = TO_PROCESS - car.cur_cm      # 从最后一个料位直接前进
# s7_finish
fwd = TO_FINISH  - car.cur_cm
```

**这样出区后的绝对位置与老流程完全一致** → 后面所有段（自旋、进加工区…）里程一个都不用改。
实测：最后在 24cm → `fwd(56)`；在 12cm → `fwd(68)`；在 0cm → `fwd(80)`（= 老行为）。

**省**：原料区、加工区各少一次 48cm 的往返 → 约 96cm 行驶，4~6s。

> ⚠️ `car.fwd()/back()` **不更新** `cur_cm`（只有 `goto_cm()` 记账）——
> 这是既有约定：进区时手工 `car.cur_cm = 0.0`，区间内一律用 `goto_cm()` 绝对定位。

#### (4) 原料区也成组（2026-09-18 晚，车主："只有加工区的三次动作成组了，原料区还没有"）

把"归零并进动作组第①步"抽成公共函数 **`grab_demo.merge_zero_into_steps()**，两个区共用：

- `place_demo.do_pick_from_rack` —— 加工区取料
- `route_main.s3_material` —— 原料区放物架（原来这里还是 `rack_zero()` 串行）

原料区改造后实测：

```
步数=9（未增步）
第①步 = ['par', [['lift_up', 2800, 40],
                  ['axis', 4, 1, 178, 80],     ← base 回正
                  ['axis', 1, 0, 212, 40]]]    ← 伸缩回正
```

> **⚠️ 一个必须配套的坑**：并行组里的 base 动作**必须立刻记进软跟踪**，
> 否则紧接着的第②步 `("base_right", …)`（`_run_rack` 把它变成**绝对角定位**）
> 会按**旧的** base 角度算差值，多转一个归零偏移量。
> 所以 `_run_rack` 新增 `_track_par_base()`，处理完 par 步骤自动补账。
> 实测：起点 87°（瞄准后）→ 第②步按 **84°** 算差值（右转 2595 脉冲 ≈ 49°），
> 而不是按 87° 算 2755 脉冲 —— 最终精确回到 90.0°。

#### (6) 速度再提 + 等待收紧；瞄准等待反而延长（2026-09-18 晚）

车主两条要求恰好对应**两组独立参数**（所以不冲突）：

**① 动作组等待收紧 + 各轴速度提升**

| `TTL_ACC_RPM_PER_S` | 300 | **500** | 车主反馈等待过长 ⇒ 实车加减速比 300 估的快 |
| `TTL_TIME_EXTRA_S` | 0.25 | **0.15** | 固定余量减半 |
| `TTL_EXTRA_S["gantry"]` | 0.6 | **0.35** | 龙门专项裕量收紧（速度已提到 60） |

取料动作组逐步实测（不含舵机）：**15.53s → 11.80s，省 3.73s（24%）**。
（`lift_up 2800@60` 2.43→1.61、`arm_in 6500@240` 2.19→1.62、`lift_down 2800@40` 2.43→1.97）

**② 瞄准每拍等待延长**

#### (7) ★加工区瞄准模式用错 → 三个靶位"零修正假收敛"（2026-09-18 晚，最严重的一次）

**现象**：加工区三个靶位的瞄准日志全是 `offset={'base': 0, 'arm': 0}`，
**一个动作都没发**，却报"收敛 ✓"。

**证据链**：
1. 诊断帧 `aim_fail/T2_213400_raw.jpg`：标靶是「**同心虚线圆环**」
   （红环左 / 绿环中 / 蓝环右，三个靶位同框），**中间是空的**；
2. `place_demo.do_aim_target` 传的是**颜色名** → 走 `aim` 的 `mode="color"` ——
   那是找**实心色块质心**的算法 → 圆环的填充率 / 圆度过不了形状判据 → **每帧都检测不到**；
3. `BlobTracker` 的 stale 保持（`vision.py:288`）在连续丢失 ≤ `stale_max`(10) 帧内，
   把**上一轮的中心**当作 `found=True` 返回（`conf=0.5` / `held=True`）→
   上层算出"已经在画面中心附近"（`dx=-2.9 dy=+6.3`，都在容差 8px 内）→
   **三阶段各一拍"达标" = 零修正假收敛**。
   （日志里 `stale=1,2,3` 递增就是铁证）

**修法（两处）**：
- **`place_demo.do_aim_target` 改用 `mode="ring"`** ——
  `RingDetector` 的 `close_k=9` 闭运算就是**专门把虚线同心环连成实心环带**再取最小外接圆心的；
  `center_gate_r` 只认画面中心附近的环 → 三个靶位同时入镜也不会认错。
  `TARGET_COLOR` 保留，只用于日志与"标靶颜色 vs 这块料颜色"的一致性检查。
- **`aim.py` 新增通用防护**：`stale > 0` 或 `held=True` 的帧**既不判断也不动作**，
  等真实检测回来；连续 `AIM_STALE_GIVEUP`(6) 拍仍如此 → **明确放弃并存诊断帧**。
  ★这条是通用的：以后任何"视觉一时看不到"的情况都不会再静默假收敛。

**实测对比**（板下 dry-run）：

```
改前：[T3#1] dx=-2.9 dy=+6.3 → 收敛 ✓  offset={'base': 0, 'arm': 0}      ← 零动作假收敛
改后：[T1#1] dx=+64.0 → [T1#2] dx=-0.2 → 收敛 ✓  offset={'base': -178, 'arm': -212}
```

> **`PLACEMENT_MAP` 的最终规则（2026-09-19 车主）**：
> "将加工区三个物料摆放改为**颜色对应摆放**（只动这里）" ⇒ **同色对齐**
> `{"1":1, "2":2, "3":3}` —— 1 号料(红)→1 号靶(红)、2 号料(绿)→2 号靶(绿)、3 号料(蓝)→3 号靶(蓝)。
> （2026-09-18 曾短暂用过"交叉" `{"3":1,"2":2,"1":3}`，已被本次取代。）
> 副作用（好事）：`COLOR_OF` 与加工区 `TARGET_COLOR` 天然一致，物架号恰好 == 靶位号；
> `route_main` 里那句"交叉放置"的说明也**改回了 ⚠️ 告警** —— 同色规则下一旦触发，
> 说明配置被改乱了、放置位置真的会错。要回到交叉规则，把那行改回 `{"3":1,"2":2,"1":3}` 即可。

### 2.8 路线节奏：启动区等回车 + 去扫码区的路上转 base（2026-09-18 晚）

**① 启动区加"等回车"**（车主："初始化完之后不要直接右移出启动区，需要等我在 ssh 终端里
打个回车再动"；随后又明确："**我指的是在 auto 模式里加入最一开始的回车等待**"）。

做法 —— **两种模式都只等一次，且 `--auto` 也等**：
- `s1_out` 里 `if not getattr(car, "auto", False): car.pause(...)`（非 auto 由它负责）
- `main()` 的段循环**之前**：`if a.auto and max(1,a.start)==1: car.pause(..., auto=False)`
  （传 `auto=False` = **强制**等，不受 `--auto` 影响）

实测：
| 模式 | 提示 | 等回车 |
|---|---|---|
| `--auto` | `按回车开跑（q=退出）` | ✓ 一次 |
| 默认 | `按回车再右移出启动区` | ✓ 一次 |

`--start 2` 起不触发（从中间段开始不用等）。

**② base 180° 挪到"去扫码区的路上"**（车主："改为在去扫码区的路上进行 base 180 度旋转…
因为车辆前进和 base 旋转不一定同时完成，等二者全部动作完成之后再进行后面的操作"）。

利用**固件 TTL 命令本来就是非阻塞**这个事实：

```python
_t0 = time.time()
_t_base = car.base_cw(BASE_180, TTL_VEL, wait=False)   # ① 只发不等，返回估算耗时
car.fwd(TO_SCAN)                                        # ② 阻塞等底盘到位
_left = _t_base - (time.time() - _t0)                   # ③ 谁慢等谁，补差额
if _left > 0:
    time.sleep(_left)
```

实测（板下）：

```
[扫码] ① 先把 base 顺时针 180° **发出去不等**，同时车开始前进（两者并行）
→ 扫码朝向 9600 脉冲 @80RPM  ★只发不等（与底盘动作并行）
→ 前进 33cm
[扫码] ② 前进已到位，base 还差 2.72s → 等它转完（两者取慢的）
```

base 180° @80RPM 本身要 **2.72s**（9600 脉冲 = 匀速 2.25 + 加减速 0.32 + 余量 0.15）；
只要底盘 33cm 比它慢，这 2.72s 就**完全省下来**。

**配套改动**：`route_car.base_turn()` 增加 `wait` 参数（`wait=False` = 只发不等、
返回估算耗时）；`car.py` 补上 `base_cw/base_ccw`（原来只有 `RouteCar` 有，现在两个类能力一致）。

> ⚠️ **踩坑记录**：`route_car.py` 里**没有** `AXIS_BASE` 这个名字（它只在 `car.py` 定义，
> 而 `route_car.py` 只有 `from car import Car`，且在 `except` 分支还会把 `Car` 置 `None`）。
> 写 `self.fire_axis(AXIS_BASE, …)` 会直接 `NameError` 崩在第 2 段。
> 该函数里必须用**数字 4**（与下面那行 `self.lower.ttl(4, …)` 一致）。

**③ 底盘命令耗时自检（2026-09-18 晚）**：车主报"经常在向右平移出启动区后长时间停止延时"。

排查结论：底盘命令是**同步**的 —— 固件 `chassis.c` 的 `Chassis_MoveX_cm()` 末尾是
`Ramp_WaitDone(&axis_chassis)`，**等到位才回 ACK**；所以上位机 `lower.move()` 里的
`send(timeout=10.0)` 正常只消耗实际运动时间（11cm ≈ 0.5~1.5s）。

于是"长时间停止"只有两种可能，加个计时就一眼分得开：

- **段间在等回车**（没用 `--auto`）：段循环末尾 `input("按回车走下一段")`。
  提示已改成醒目的 `⏸ 【本段完成 —— 等你按回车才走下一段】`
  （原来缩进小、混在滚动日志里，看着像卡死）。
- **ACK 丢了 / 固件到位判据慢**：`_send_once` 等满 timeout 会打印
  `!! ACK 超时 cmd=0x01（10.0s）`。

新增自检：`fwd/back/left/right/spin` 超过 **1.2s** 就打印
`⏱ 【右移11cm】花了 2.0s —— 底盘命令偏慢！`（实测正常不打印、假装卡 2s 会触发）。

> ⚠️ **必须两处都加**：`route_car.RouteCar` **自己 override 了**这五个底盘函数，
> 只改 `car.py` 那份对跑图**不生效**。
