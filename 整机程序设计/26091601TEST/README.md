## 1. 这个工程是什么

一台智能搬运小车的**下位机**：接收上位机（RDK X5）发来的 10 字节命令，驱动

- **底盘 4 轮**（步进 + 加减速引擎 `ramp.c`）
- **3 个 TTL 闭环电机**（伸缩滑台 / 龙门架升降 / base 回转，走 `Emm_V5` 协议）
- **2 个舵机**（夹爪 / 腕关节）

### 设计原则（2026-09 定）

> **调参与动作组设计尽量放上位机，下位机只留空函数接口。**

所以本工程相对早期版本多了两块"给上位机用"的东西：

| 新增 | 作用 |
|---|---|
| `CLEAN\params.c/h` | **参数表**：速度 / 脉冲 / 加速度等，上位机用 `0x20` 下发、`0x22` 读回 |
| `CLEAN\motion.c/h` | **动作组解释器**：步骤表由上位机用 `0x21` 下发，`0x24` 触发执行 |

## 4. 编译与烧录（★按顺序，别跳步）

1. **Keil5 打开** `USER\26091601TEST.uvprojx`
   （**不用再加文件**，`params.c` / `motion.c` 已经在 CLEAN 组里了）
2. **Project → Rebuild all target files**
   —— 是 **Rebuild**，不是 Build！改了头文件/加过文件时 Build 可能不重编
3. 看 **0 Error**（warning 可以容忍，但新增 warning 要看一眼）
4. **★确认 `OBJ\26091601TEST.hex` 的时间戳 = 刚刚**
   —— 这一步别省。**"烧了旧 hex 白查几小时"是这个项目最经典的坑。**
5. 烧录（ST-Link / J-Link，按 `Options → Debug` 里的设置）
6. **架空车轮**先测：
   - 上位机 `lower_api` 发单条命令，看各轴动作方向对不对
   - 再跑动作组：`l.run_group("HOME")` 之类
7. 最后接视觉，跑上位机主程序

### 4.1 ★ 5 秒自检：板子里烧的是哪一版固件？

**烧错版本是"白查几小时"的头号原因**，而发一条命令就能判断 —— 不用拆车、不用重烧：

```text
下发：FF 22 00 01 00 00 00 00 00 FE      （0x22 = 读参数，id = 1）
```

| 回帧 | 结论 |
|---|---|
| **10 字节**：`FF 22 idH idL v3 v2 v1 v0 FE` | ✅ **新固件**（`26091601TEST` 及以后 —— 有 `0x22` 这个 case） |
| **3 字节**：`FF 01 FE` | ❌ **旧固件**（`26090901TEST` 及更早 —— **没有 `0x22`**，回的是统一 ACK） |

> ⚠️ `0x22` 的回帧**必须按 10 字节定长读** —— 32 位**值里本身就可能含 `0xFE`**，
> 只靠"找包尾 `0xFE`"会误截。上位机 `lower_api.query()` 已按这个布局实现（见 `doc/02`）。

**编译产物参考值**（用于对照是否真的重编了）：

| 项 | 值 |
|---|---|
| Program Size | `Code=17652`（0 Error / 1 Warning —— Warning 是未引用的 `Debug_ManualSeq`） |
| hex 输出 | `OBJ\26091601TEST.hex`（当前这份编译于 **2026-09-17 16:38:09**） |
| 底盘换算 | `STEPS_PER_CM` = 130 |

### 烧录后的自检建议

| 检查项 | 期望 |
|---|---|
| 底盘前进 10cm | 四轮同向，实测 ≈10cm |
| 底盘旋转 90° | 实测 ≈90°，误差大就调 `STEPS_PER_DEGREE` |
| 龙门架 | 上行/下行方向正确，限位不顶死 |
| 伸缩滑台 | 伸出/缩回方向正确 |
| base 轴 | **正转（dir=0）= 左转/逆时针** |
| 夹爪 | `0x14` 开/闭方向对；`0x15` 设角度生效（**角度越小 = 爪片张得越开**） |
| 参数读回 | `0x22` 读某个 ID，值与下发一致 |

## 5. 命令字速查

完整说明见 `..\VisualBot2\doc\02_通信协议与下位机.md`。这里只列命令字，方便对照 `car_config.h`：

| 段 | 命令字 | 说明 |
|---|---|---|
| 底盘 | `0x01` `0x02` `0x03` | 纵向 cm / 横向 cm / 旋转 度 |
| 底盘精细 | `0x05` `0x06` | mm 级 |
| **TTL 闭环** | `0x10` | id1 **伸缩滑台** |
| | `0x11` | id2+id3 **龙门架**（固件自动反向传动） |
| | `0x12` | id4 **base 回转** |
| | `0x13` | 放料动作组（整组：下放-开爪-抬升） |
| | `0x14` | 夹爪开/闭（`buf[1]`=0 开 / 1 闭） |
| | `0x15` | 夹爪设任意角度（`buf[1]`=0~255°） |
| | `0x16` | 去车载物架夹料动作组（`buf[1]`=物架位 1/2/3） |
| **校赛扩展** | `0x20` | 下发参数（`buf[1..2]`=ID 大端，`buf[3..6]`=值 32 位大端） |
| | `0x21` | 下发动作组步骤（子类型 0 清空 / 1 步头 / 2 补脉冲 / 3 提交） |
| | `0x22` | 读参数（回 10 字节值帧，**不走统一 ACK**） |
| | `0x23` | 参数存 Flash（可选实现） |
| | `0x24` | 执行动作组（`buf[1]`=组号，`buf[2]`=slot） |
| 显示 | `0x04` | 显示二维码 |
| **死代码** | `0x07` `0x08` `0x09` `0x0A` `0x0B` `0x0C` `0x0D` | 老师车遗留（转盘/地面抓取/升降预设位/载物台旋转），**本车没有这些机构，别调用** |

### 5.1 帧布局（★`buf[0]` 是命令字本身，不是第一个参数！）

```text
 FF   buf[0]=cmd   buf[1] buf[2] buf[3] buf[4] buf[5] buf[6] buf[7]   FE
 │    命令字        └──────────── 7 字节参数 ────────────┘             │
 └─ 帧头                                                     帧尾 ─┘
```

⚠️ **本工程代码里 `buf[0]` 对应命令字、`buf[1] ~ buf[7]` 才是那 7 个参数字节**
（差一位就全错，**"已经踩过一次错位"**）。

- **`0x20 ~ 0x24` 的逐字节对照表**在 **`README_校赛扩展.md` §三"帧布局对照表"** —— 两边必须一致，照抄即可。
- **`0x22` 读参数的回帧是定长 10 字节**：

  ```text
  FF  22  idH idL  v3 v2 v1 v0  FE
  ```

  > 上位机侧 `lower_api.query()` 按这个布局取值。**不能只靠"找包尾 `0xFE`"来截断** ——
  > 因为 32 位**值里本身就可能含 `0xFE`**，会被误当成帧尾。

## 6. 机械结构真相（★别按"老师那套"想当然）

| 部位 | 实现 | 协议 | 单位 |
|---|---|---|---|
| 伸缩滑台 | TTL 闭环 **id1** | `0x10` | 脉冲 / RPM |
| **龙门架升降** | **TTL 闭环 id2 + id3 两台反向传动** | `0x11`（固件自动 id2=dir、id3=反向） | 脉冲 / RPM |
| base 轴 | TTL 闭环 **id4** | `0x12` | 脉冲 / RPM |
| 夹爪 / 腕关节 | **舵机** Servo2 / Servo3 | `0x14` 开闭、`0x15` 角度 | **角度 0~255°** |
| 底盘 4 轮 | 步进 + `ramp.c` | `0x01`/`0x02`/`0x03` | cm / 度 |

⚠️ **本车没有独立步进升降轴、没有载物台旋转电机**（载物台固定，3 个号位）。
`claw.c` 的 `Lift_GoTo` / `Tray_Turn120` / `Claw_*` 与协议 `0x07/0x09/0x0B/0x0C` 都是**老师车遗留死代码**。
夹爪一律走舵机（`Grip_Close/Open` 现在会**优先读参数表** `P_GRIP_*_ANGLE`）。

## 7. 两个关键机制

### 7.1 TTL 命令是**非阻塞**的

`TTLctrl.c` 对 `0x10/0x11/0x12` 的处理是"**发完即返回，不等待**"（源码注释原文）。
这意味着：

- 上位机**不能**靠"等 ACK"来判断动作完成 → 只能**按时间估算**
- 好处：天生支持**多轴并行**（上位机把三条命令连续发出，三个轴同时动）
- 坑：估算公式必须把**加减速段**算进去（`car_config.h` 的 `TTLCTRL_ACC_DEFAULT=60`，非 0 → 带加减速）。
  早期公式只算匀速段，速度调高后严重偏短 → 现场症状"伸缩台还没到位，龙门架和舵机动作就开始执行"。
  上位机侧已修（`car.py` 的 `ttl_time()`），详见 `doc/06`。

### 7.2 底盘命令是**同步**的

`chassis.c` 的 `Chassis_MoveX_cm()` 末尾是 `Ramp_WaitDone(&axis_chassis)` —— **等到位才返回**，所以 ACK 在动作完成后才发出。
上位机 `lower.move()` 的 `send(timeout=10.0)` 因此会阻塞到车到位（正常只花实际运动时间）。
若 ACK 丢失，会白等满 10 秒 —— 上位机侧有耗时自检（`⏱`）与超时日志用于区分。

## 8. 上位机配套要求

本固件对应的上位机协议层是 `整机程序设计\校赛\lower_api.py`，已适配：

- **ACK 判定同时接受** `FF 01 FE`（旧固件统一回执）与 `FF <cmd> … FE`（新固件回显命令字）
- **`0x22` 读参数按 10 字节定长读** —— 因为值里可能含 `0xFE`，只靠包尾会误截

`sync_profile()`（部分版本里叫别的名字）会在发车前下发全部参数与动作组，并对关键参数读回校验；
**校验不一致会拒绝发车** —— 那时先查参数 ID 与帧布局，别硬跑。

> ⚠️ **参数表的"唯一真源"已经变了**：
> 早期文档（`README_校赛工程.md`）说 `motion_profile.json` 是唯一真源，那是**状态机版 `school_flow.py`** 时代的事。
> **现在主程序是跑图版 `route_main.py`，参数写在各调试器的参数区**（`grab_demo.py` / `place_demo.py` / `route_main.py`），
> 由 `build_car()` 在启动时注入。详见 `..\VisualBot2\doc\03_上位机工程.md` 与 `06_调参手册与常见故障.md`。
