# 01 系统总览

> **一句话**：RDK X5 当"眼睛和大脑"（视觉识别 + 路线规划 + 动作编排），STM32F103ZET6 当"手脚"
> （步进脉冲 / TTL 闭环电机 / 舵机），两者用 **10 字节定长帧**串口通信。
> 校赛（2026-09）已完整跑通"取三块料 → 放到三个标靶"的全流程。

## 1. 两台机器

| 角色 | 硬件 | 系统 / 环境 | 干什么 | 代码在哪 |
|---|---|---|---|---|
| **上位机** | RDK X5（D-Robotics，8×A55） | RDK OS，Python 3，OpenCV 4.11（**无 GStreamer**） | 相机取帧、圆环/颜色/二维码识别、瞄准闭环、里程走位、动作组编排、浏览器调参台 | 板上 `/root/VisualBot3`（本地副本 `整机程序设计\VisualBot2\`） |
| **下位机** | STM32F103ZET6 | Keil5 / 裸机 | 接收 10 字节命令 → 步进加减速、TTL 闭环电机、舵机、WS2812、OLED | `整机程序设计\26091601TEST\` |

**分工原则**（2026-09 定）：**调参与动作组设计尽量放上位机，下位机只留空函数接口**。
下位机的 `params.c` / `motion.c` 就是为此加的"参数表 + 动作组解释器"。

## 2. 整车硬件

### 2.1 执行器清单（★别按"老师那套"想当然）

| 部位 | 实现 | 协议 | 单位 |
|---|---|---|---|
| 伸缩滑台 | TTL 闭环 **id1** | `0x10` | 脉冲 / RPM |
| **龙门架升降** | TTL 闭环 **id2 + id3 两台反向传动** | `0x11`（固件自动 id2=dir、id3=反向） | 脉冲 / RPM |
| base 轴（回转） | TTL 闭环 **id4** | `0x12` | 脉冲 / RPM |
| 夹爪 / 腕关节 | **舵机** Servo2 / Servo3 | `0x14` 开闭、`0x15` 任意角度 | **角度 0~255°** |
| 底盘 4 轮 | 步进 + `ramp.c` 加减速 | `0x01` / `0x02` / `0x03` | cm / 度 |
| 载物台（车载物架） | **固定**，3 个号位 | — | — |

⚠️ 本车 **没有**独立步进升降轴、**没有**载物台旋转电机。
`claw.c` 的 `Lift_GoTo` / `Tray_Turn120` / `Claw_*` 与协议 `0x07 / 0x09 / 0x0B / 0x0C` 是**老师车遗留死代码，别调用**。

### 2.2 相机（USB，UVC）

| 型号 / VID:PID | 用途 |
|---|---|
| `LRCP G720P`（`0c45:1915`，Microdia） | **作业相机** —— 找物料色块、找标靶圆环 |
| `LRCP G-720P`（`1e45:5487`） | **扫码相机** —— 读二维码 |

> ⚠️ **★设备节点会变，绝对不能写死。**
>
> 每台 UVC 相机会占用**一对** `/dev/videoN`（一个视频流 + 一个元数据节点），具体落在哪一对
> 取决于**插拔顺序和 USB 口**。同一台机器上换个口，`video0` 就可能变成 `video2`。
>
> **2026-09-22 实测**：只插了作业相机时，`v4l2-ctl --list-devices` 显示它落在
> **`/dev/video2` + `/dev/video3`** —— 而早期记录里它一直在 `video0` / `video1`。
> （也就是说：**文档里写的具体节点号只能当参考，一律以现场实测为准。**）
>
> **每次开工先跑这一条确认**：
>
> ```bash
> v4l2-ctl --list-devices      # 权威列表：哪个型号 → 哪几个 /dev/videoN
> ls /dev/video*
> ```
>
> 然后按结果改这几处：
> - `route_main.py` 的 `CAM_INDEX`、`MONITOR_SCAN_CAM`
> - 各调参台的启动参数 `--cam N`
> - 代码里 `open_camera()` 的索引

⚠️ **相机索引会变**，这是"程序启动说相机打不开"的头号原因。
⚠️ **曝光**：写死的 `156` 会过曝（实测 45% 像素过曝，红料被洗成粉白、质心乱飘）→ 作业用 **30**。

### 2.3 通信链路

```
   [作业相机]──USB──┐
                    ├── RDK X5 ──USART(115200-8N1, /dev/stm32)── STM32F103ZET6 ──USART3(115200)── Emm_V5 ×4
   [扫码相机]──USB──┘        上位机                                   下位机                        TTL 闭环电机
```

- 上位机 ↔ 下位机：**`/dev/stm32`**（udev 别名，指向实际的 `/dev/ttyUSB*` 或 `/dev/ttyACM*`）
- 下位机 ↔ Emm_V5：`USART3`，PC10/PC11（见 `26091601TEST\README.TXT`）
- 引脚速查以 `26091601TEST\README.TXT` 与 `CLEAN\car_config.h` 为准

## 3. 坐标与方向约定（★最容易搞错）

### 3.1 轴号与方向

```python
AXIS_ARM    = 1     # 伸缩滑台（TTL id1）
AXIS_GANTRY = 2     # 龙门架升降（TTL id2+id3，固件自动反向）
AXIS_BASE   = 4     # base 回转轴（TTL id4）
FWD, REV = 0, 1     # 固件层：0=正转 / 1=反转
```

- **base 轴**：`FWD` = **左转 / 逆时针**（从上往下看）；`REV` = 右转 / 顺时针
- **脉冲换算**：`3200` 脉冲 / 圈（Emm_V5 默认细分）；`BASE_90 = 4800` 脉冲 → **1° ≈ 53.3 脉冲**
- **动作组里的别名**（见 `car.py` 的 `_STEP_ALIAS`）：`lift_up` / `lift_down` / `arm_in` / `arm_out` / `base_left` / `base_right` / `grip_open` / `grip_close`

### 3.2 画面坐标

- 作业相机实际输出 **1280 × 720**，画面中心 = **(640, 360)**，**y 轴向下为正**
- 处理时按性能档缩到 512（rdk 档 `proc_scale = 0.34`）
- 瞄准的目标点 = 画面中心 + `CAM_GRIP_OFFSET_X/Y`（夹爪与光轴不共轴的**像素**补偿）

### 3.3 里程软跟踪（★算错会导致后面所有段错位）

```python
car.cur_cm          # 纵向里程（cm），**只由 goto_cm() 记账**
car.fwd(cm)         # ★不更新 cur_cm
car.back(cm)        # ★不更新 cur_cm
```

- 进原料区 / 加工区时**手工** `car.cur_cm = 0.0`
- 跑完三个工位**就地停下**，不回 1 号位；出区时用 `fwd = TO_XXX - cur_cm` 把差额补上
- 这样**出区后的绝对位置与老流程完全一致**，后面所有段里程不用改

### 3.4 base 角软跟踪

- base 轴**没有编码器反馈**，全靠软件记账（`base_deg`）
- 动作组里 base 步骤走**绝对角定位**（`goto_base_deg`），不是相对脉冲
- 并行组里的 base 动作不会自动记账 → `_run_rack()` 的 `_track_par_base()` 会扫 `("par", [...])` 子步补记

### ⚠️ 共享库有"两份拷贝"，改完必须同步

下面这 10 个共享库文件在 `校赛\` 和 `VisualBot2\` 里**各有一份，md5 完全相同**：

| 文件 | 作用 |
|---|---|
| `aim.py` · `vision.py` · `car.py` · `lower_api.py` · `school_config.py` · `cam_rotate.py` · `qr_scan.py` · `ledger.py` · `check_env.py` · `exposure_tune.py` | 瞄准 / 视觉 / 动作库 / 协议层 / 参数 / 方向 / 扫码 / 账本 / 环境检查 |

**为什么会有两份**：
- **`校赛\` 是"源"** —— 部署脚本 `deploy_visualbot2.ps1` 里的 `$SCHOOL` 指向它
- **`VisualBot2\` 里那份是部署/同步的产物** —— 而 demo 运行时 `sys.path` 优先当前目录，
  所以**实际被 import 的是 `VisualBot2\` 这一份**

**⇒ 改共享库的正确做法**：

1. 改 **`校赛\`**（源）
2. **同步**到 `VisualBot2\`：`Copy-Item 校赛\xxx.py VisualBot2\ -Force`
3. 确认两边 md5 一致，再部署

> ⚠️ 只改一边会出现"本地看着改了、板上跑的却是另一份"的经典混乱。
> 快速自检（在 `整机程序设计\` 下跑）：
>
> ```powershell
> foreach ($f in @("aim.py","vision.py","car.py","lower_api.py","school_config.py")) {
>   $h1 = (Get-FileHash "校赛\$f" -Algorithm MD5).Hash
>   $h2 = (Get-FileHash "VisualBot2\$f" -Algorithm MD5).Hash
>   $tag = "一致"; if ($h1 -ne $h2) { $tag = "★不一致" }
>   "{0,-20} {1}" -f $f, $tag
> }
> ```

**另外，两边各有"独有"文件**：

| 只在哪 | 文件 | 性质 |
|---|---|---|
| **只在 `校赛\`** | `school_flow.py`、`school_main.py`、`calibrate_route.py`、`pick_debug.py`、`test_school_local.py`、`test_school_main_local.py` | 校赛早期的**状态机版 / 流水账版**主程序，跑图版不用（保留作参考） |

## 5. 一次"取→放"的完整链路

以加工区放置一个物料为例（`place_demo.run_one()`）：

```
① 回 90° 作业位          goto_base_deg / base_left          base 轴
② 瞄准标靶               aim.converge() 三阶段 X1→Y→X2       base + 伸缩
   └─ 用 mode="ring" 找**圆环中心**（★不是色块！）
③ 归零                   replay(off, -1)                     把瞄准的偏移还回去
   └─ 得到"夹料的确定起点"
④ 去车载物架夹料         反向动作组（11 步）                  伸缩+龙门+base+夹爪
   └─ 归零并进第①步 → 三轴并行
⑤ 回放到靶心             replay(off, +1)                     把料送回瞄好的位置
⑥ 放置                   下放 → 松爪 → 抬回                  龙门 + 夹爪
⑦ 回零                   replay(off, -1) 或 goto 90°         消除伸缩偏移
```

**为什么顺序必须这样**（踩过的坑）：
- 原先写成 `回作业位 → 夹料 → 瞄准 → 放置`，**瞄准算出的偏移完全没被用上**
- **必须归零**：瞄准会用**伸缩**修画面 y（offset 常有几百脉冲），而动作组里 `arm_in` 是**相对**位移；
  不归零的话每次落点都不同，还可能撞物架
