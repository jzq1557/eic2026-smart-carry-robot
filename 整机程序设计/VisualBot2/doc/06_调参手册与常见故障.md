# 06 调参手册与常见故障

> **一句话概括**：现场调参的全部难点不在"改哪个数"，而在**改的这个数到底会不会生效** ——
> 参数分散在四层（`grab_demo.py` 参数区 / `place_demo.py` 自带一份 / `school_config.py` / 两个 JSON 档案），

## 一、参数分四层 —— 先看地图，再动手

### 1.1 四层地图

### 1.2 ★ 铁律：不在白名单里 = 改了不生效（踩过两次）

`grab_demo.build_car()` 里做注入，**注入清单是硬编码的两个元组**：

```python
SC.K_PX2STEP_BASE = K_BASE
SC.K_PX2STEP_ARM  = K_ARM
for _k in AIM_KEYS + VISION_KEYS:
    setattr(SC, _k, globals()[_k])      # ← 只有这两个元组里的名字被搬进 school_config
```

- `AIM_KEYS` 共 **24 项**：`AIM_TOL_PX`、`AIM_OUT_MAX_PX`、`AIM_SETTLE_S`、`AIM_MAX_ITER`、`AIM_RETRY`、
  `AIM_PROBE_PULSES`、`AIM_VEL_BASE`、`AIM_VEL_ARM`、`AIM_WARMUP_FRAMES`、`AIM_FLIP_BASE`、`AIM_FLIP_ARM`、
  `AIM_DAMP_MAX_FLIP`、`AIM_READ_FRAMES`、`K_R_SCALE`、`K_R_REF`、`AIM_STAGE_CONFIRM`、
  `AIM_DAMP_MAX_FLIP_ARM`、`AIM_ARM_LIMIT_SCALE`、`AIM_SOFT_ZONE_PX`、`AIM_SOFT_GAIN`、
  `AIM_LIMIT_STAGES`、`AIM_WARMUP_JITTER_PX`、`AIM_WARMUP_SETTLE_S`、`AIM_STALE_GIVEUP`
- `VISION_KEYS` 共 **5 项**：`COLOR_MED_N`、`COLOR_EMA`、`COLOR_JUMP_PX`、`COLOR_STALE_MAX`、`CAM_FLUSH_FRAMES`

**两次真实事故**：

1. `AIM_LIMIT_STAGES`（分段限幅）曾不在 `AIM_KEYS` 里 → 在参数区把分段限幅改成"提速版"**根本不生效**，
   一直用 `school_config.py` 那份；更坑的是菜单 `k` 打印的是 `SC` 上的值，**数字会骗人**。
2. 同名参数在 `school_config.py` 里有旧值 → 只要漏进白名单，参数区的新值就是"死代码"。

**操作判据**：改完任何 `AIM_*` / `K_*` / `COLOR_*` / `CAM_FLUSH_FRAMES`，在 demo 菜单里打
**`k`**（grab_demo / place_demo 都有）看 `SC` 上**实际生效**的值，与参数区一致才算改对。

### 1.3 ★ 三个"看起来改了其实没改"的静默回退

| 写法 | 实际结果 |
|---|---|
| `LIFT_UP = getattr(RM, "LIFT_UP", 4400)` | `route_main.py` **没有** `LIFT_UP` 这个键 → **静默回退**成默认值；在 `route_main.py` 里加这个键才会被读到 |
| `K_BASE = getattr(RM, "K_BASE", SC.K_PX2STEP_BASE)` | `route_main` 没有 `K_BASE`（跑图用不上）→ 静默回退成 `school_config` 里**老师那台车**的旧值 `0.2593` |
| `BASE_90 = getattr(RM, "BASE_90", 4800)` | `route_main.BASE_90` **确实存在**（4800）→ 改 `route_main` 的 `BASE_90` / `TTL_VEL` 会连带影响 `grab_demo`（但不影响 `place_demo`） |

规律：**`getattr(某模块, 名字, 兜底值)` 只有在那个模块真有这个键时才生效**。不确定就 `grep` 一遍。

### 1.4 档案的"全量覆盖"语义

| 工具 | 端口 | 写档案的方式 | 后果 |
|---|---|---|---|
| `ring_stream_ui.py`（圆环调参台，8091） | 8091 | `/save` → `json.dump(st.cfg)`，`st.cfg` 是**面板上全部 CALIB 项的当前值** | **全量重写** `ring_calib.json`：面板上没暴露的项，写回的是"从 CALIB 初值来的那份" |
| `target_stream_ui.py`（彩色标靶台，8091） | 8091 | `save_profile()`：先读旧文件 → 覆盖 `red/green/blue` 三段 + `_tune` → 写回 | 三色阈值 + `_tune` 被整体替换；其它键保留 |
| `color_blob_stream.py`（颜色台，8090） | 8090 | `/save` → `dict(PRESETS)` + `_tune = snapshot_params()` | 6 色 PRESETS + `_tune` 整体替换（`_tune` 是 2026-09-18 才补上的，早先**只存颜色阈值、形状参数全丢**） |
| 监控台画面方向按钮 | 8092 | `cam_rotate.save_mode()`：读旧 `ring_calib.json` → 只改方向键 → 写回 | 只动方向，不动其它参数 |

**结论**：调完方向/阈值**一定点"保存档案"**，然后**重启主程序**（档案在创建相机时读一次）。
换机器（Pi / Jetson / RDK）时 `ring_calib.json` / `color_profile.json` **同名不同内容**，别互相覆盖。

### 1.6 改完参数之后的标准动作（每次都做）

1. 确认改的是**哪一层**（§1.1），尤其先确认名字在 `AIM_KEYS`/`VISION_KEYS` 里；
2. `python3 -m py_compile <file>` 或直接重跑（部署脚本也会远端 `py_compile`）；
3. 重启进程（瞄准/滤波类只有少数能用 `k` 热改）；
4. 菜单打 **`k`**（或看启动日志里的参数回显）确认**实际生效值**；
5. 参数区改完立刻 `git commit`（2026-09-19 起本工程已入 Git），`git diff` 是唯一可信的"到底改了哪一行"。

## 二、△ 两组等待参数千万别搞混

| | **动作组等待**（机械到位） | **瞄准等待**（视觉节奏） |
|---|---|---|
| 参数 | `TTL_ACC_RPM_PER_S`、`TTL_TIME_EXTRA_S`、`TTL_EXTRA_S` | `AIM_SETTLE_S`、`AIM_WARMUP_SETTLE_S` |
| 在哪 | `school_config.py` | `grab_demo.py` 参数区（白名单内） |
| 管什么 | TTL 单轴命令（0x10/0x11/0x12）**发出去之后等多久才算走完** | 瞄准每一拍之间 / 预热每帧之间**等多久再读帧** |
| 影响的现象 | 动作组里**两步之间**等多久；底盘命令的总耗时 | 瞄准总时长、单拍决策是否基于"停稳后的画面" |
| 典型症状 | 等太短 → "没到位就下一步"（夹爪在半空闭合、伸缩还在飞）；等太长 → 全程慢、车主报"等待过长" | 等太短 → 读到机械余振帧 → **第一拍方向反** / 过冲振荡；等太长 → 车主报"每次都好几轮，很卡" |

**为什么必须分开**：两者治的是**完全不同**的病，而且最优值方向相反。

- `AIM_SETTLE_S` 是"**机械余振没停就不许读帧**"的保险，属于瞄准闭环的稳定性参数 —— 余振没停就读帧，
  等于拿假信息决策（`0.5 → 0.65` 就是这么来的）。
- `AIM_WARMUP_SETTLE_S` 是"**开工前丢几帧**"的节奏参数，判据已简化成"只看 `stale==0`"，
  **正常只走 1 帧**。它被**故意与 `AIM_SETTLE_S` 脱钩**：瞄准迭代延长到 0.65s 时，
  预热不该跟着变长（预热本身就是"越短越好"的那一段）。
- 如果两者挂钩，那么"想让瞄准更稳 → 调大 `AIM_SETTLE_S`"会**副作用式地**把预热也拖慢，
  而预热拖慢对稳定性毫无收益 —— 这就是脱钩的理由。

**判定你改错了哪一组**：

- 症状是"**机械动作还没完，下一个动作就发了**" → 改**动作组等待**那一组（§三）；
- 症状是"**画面在晃 / 瞄准第一拍朝反方向走 / 20 拍不收敛**" → 改**瞄准等待/滤波**那一组。

## 三、TTL 估时公式的来龙去脉

### 3.1 为什么必须"估"

- 下位机固件对 `0x10/0x11/0x12` 是**非阻塞**的（`TTLctrl.c` 原注释：「单轴非阻塞控制…命令立即执行，发完即返回，不等待」）
  → 上位机发完命令**拿不到"走完了"的回执**，只能**按时间估**再往下走；
- 而驱动器是**带加减速**的：`car_config.h` 的 `TTLCTRL_ACC_DEFAULT = 60`（非 0 → 不是"直接启动"）；
- **老公式只算匀速段**：`时间 = 脉冲 × 60 / (RPM × 3200)`。

误差随速度放大（同一个大行程 6500 脉冲）：

| 速度 | 匀速段 | 加减速段 | 老公式估 | 结论 |
|---|---|---|---|---|
| 40 RPM | 3.05s | ≈0.27s | 3.30s（含固定余量） | ✅ 够 |
| 200 RPM | 0.61s | ≈1.33s | 0.86s | ❌ **少等 1.3 秒** |

→ 现场症状：**"伸缩台还没到位，龙门架和舵机动作就开始执行"**（动作组顺序没写错，是估时偏短）。

### 3.2 现在的公式（`car.ttl_time()` / `ttl_wait()`）

```
总耗时 = 匀速段 + 加减速段 + 该轴裕量 (+ 每条命令固定余量)
       = 脉冲 × 60 / (RPM × 3200)          ← t_lin
       + 2 × RPM / TTL_ACC_RPM_PER_S       ← t_acc
       + TTL_EXTRA_S[轴名]                  ← t_ext
       + TTL_TIME_EXTRA_S                   ← 固定余量（只加在 sleep 里）
```

各参数物理含义：

| 参数 | 默认 | 含义 | 调大 | 调小 |
|---|---|---|---|---|
| `TTL_PULSES_PER_REV` | 3200 | 一圈脉冲数（16 细分 × 200 整步） | — | — |
| `TTL_ACC_RPM_PER_S` | **500.0** | 加减速斜率（RPM/s）；**一段**的耗时 ≈ 本步 RPM ÷ 斜率，两段合成 `2×RPM/斜率` | 等得少（更贴实车）| 等得多（更保险）|
| `TTL_TIME_EXTRA_S` | **0.15** | 每条命令的**固定**余量（通信往返 + 起停抖动） | 每条命令都更慢 | 更快，但抖一点就短 |
| `TTL_EXTRA_S["gantry"]` | **0.35** | 龙门架**按轴**的额外裕量（低转速 + 重负载：id2+id3 反向传动抬整个龙门 + 载物台，实际加减速比统一斜率估得慢） | 更保险 | 更快；太快会"龙门没下放到位就关爪" |
| `TTL_EXTRA_S["arm"]` / `["base"]` | 0.0 / 0.0 | 伸缩滑台 / base 轴的额外裕量 | 同上 | 同上 |

**现场标定法（不确定就取更小的斜率 = 等更久 = 更安全）**：

1. 发一条大行程（如伸缩 6500 脉冲 @200RPM），用秒表/录像量"从起到停"总时间 `T`；
2. 减掉匀速段得加减速总耗时 `Δ`，则 `斜率 ≈ RPM ÷ (Δ/2)`；
3. 例：`T ≈ 1.8s` → `Δ = 1.19s` → 单段 0.60s → `斜率 ≈ 333 RPM/s`。
4. 按轴的裕量：`裕量 ≈ T − (脉冲×60/(RPM×3200) + 2×RPM/TTL_ACC_RPM_PER_S)`。

`route_car._wait_axis()` 已统一改走 `Car.ttl_wait()` —— **全工程只有一套估时规则**，
改斜率/裕量对所有轴动作（含跑图）同时生效。

## 四、速度调优的边界（★重要警告）

### 4.1 可以提的（底盘 + TTL 大动作）

| 项 | 当前 | 备注 |
|---|---|---|
| `TTL_VEL` / `RACK_TTL_VEL`（base 转动） | 40 → **80** | 车主："全程序（**除瞄准**）base 速度翻倍" |
| `LIFT_UP_VEL` | 40 → **60** | 龙门抬升 |
| `LIFT_DOWN_VEL` | 30 → **40** | 下放比抬升保守：要落到料位/靶面上，太快容易冲过头 |
| `ARM_OUT_VEL` / `ARM_IN_VEL` | 200 → **240** | 伸缩是 6500 脉冲的大行程，提速收益最大 |
| `CHASSIS_VEL` / `ACC` / `DEC`（跑图） | 7 / 6 / 3 | "飘就降到 6，稳了可加到 10"；`DEC < ACC` = 刹车比起步缓，防点头丢步 |

配套实测：取料动作组 **15.53s → 11.80s（省 24%）**；归零并进第①步后 **3.7s → 2.43s**。

### 4.2 ★★ 瞄准绝不动速度

`AIM_VEL_BASE` / `AIM_VEL_ARM` **保持 40 RPM**：

- 40 RPM 下 **56 脉冲（≈1°）只要 ≈4ms**，本来就等于"瞬跳 + 急停"，步进电机容易**丢步**并**激起机械余振**；
- 相机跟着晃 → 画面不稳 → **越修越偏 / 中心来回摆**；
- 提速只会让丢步和余振更严重 —— **提速的收益（省几毫秒）远小于代价**；
- 怀疑"摇摆是机械引起"时，正确方向是**降**速：`k VEL_BASE 15`（降到 15~20 对比），不是升速。

### 4.3 超时的"回退开关"

调参是**双向**的：出现下面症状就按对应方向退回去。

| 又出现的症状 | 回退动作 |
|---|---|
| "没到位就下一步"（伸缩还在飞 / 龙门没下放到位就关爪） | `TTL_ACC_RPM_PER_S` 回 **400**；或 `TTL_EXTRA_S["gantry"]` 回 **0.5** |
| 速度太快 → 冲过头 / 失速 / 异响 | 相关轴的 `*_VEL` **各降 20%**（如 240 → 200、80 → 64） |
| 瞄准"卡"（每拍等待太久） | 降 `AIM_SETTLE_S`（0.65 → 0.5）；但若发现读到的老是"上一拍的位置"，回 0.6~0.8 |
| 瞄准在中心来回摆 | 先降 `AIM_VEL_BASE/ARM` 到 15~20；再考虑加大阻尼 `AIM_DAMP_MAX_FLIP` |

⚠️ **一条命令的等待与一条命令的速度是一对**：提速 20% 而不动斜率/裕量，
等于把这步的等待时间砍掉一截 —— 提完速度**必须**确认没有"没到位就下一步"。

## 五、底盘动作耗时自检（>1.2s 会打印 ⏱）

底盘命令是**同步**的：固件 `Chassis_MoveX_cm()` 末尾 `Ramp_WaitDone()` **等到位才回 ACK**，
所以 `lower.move()` 里的 `send(timeout=10.0)` 正常只消耗真实运动时间（11cm ≈ 0.5~1.5s）。

`car._chassis_timed()` 对 `fwd / back / left / right / spin` 计时，**超过 1.2s** 打印：

```
⏱ 【前进11cm】花了 10.2s —— 底盘命令偏慢！（正常 11cm ≈1s；先看上一行有没有 `!! ACK 超时`）
```

**这一行的用途就是分诊**：

| 上一行有没有超时行 | 结论 |
|---|---|
| 有 `!! ACK 超时 cmd=0x01（10.0s）` | **ACK 丢了/固件没回** → 白等满超时（10s）→ 查串口/USB/固件忙 |
| 没有超时行但也慢 | 固件**到位判据慢**（斜坡减速尾巴拖得久）→ 属固件/参数问题，不是通信 |

★★ **`route_car.RouteCar` 自己 override 了这五个函数** → 只改 `car.py` 那份对**跑图不生效**（踩过）。
现在两处都加了自检：改阈值/文案时**两处都要改**（`car.py` 与 `route_car.py`，行号近似，行为必须一致）。

相关超时（`lower_api.send`）：底盘 10s / 自旋 12s / 单轴 TTL 8s / 夹爪 5s / 停车 2s /
阻塞动作组 25s（`school_config.T_ACK_ACT`，0x13/0x16/0x24 要整组跑完才回，3s 会误判）。

## 六、常见故障速查表（★主体）

> 用法：先按症状找到行 → 按"查哪里"看日志/文件 → 按"怎么修"动手。**每修一项只动一个变量**再复测。

### 6.1 连接与硬件

| 症状 | 最可能原因 | 查哪里 | 怎么修 |
|---|---|---|---|
| 车完全不动 | 串口没连上 / 用错设备名 | `ls /dev/ttyUSB*`；启动日志有没有 `LowerLinkError` | 统一用 **`/dev/stm32`**（udev 规则固定，插拔不变号）；确认 TX/RX 交叉（PA9/PA10/GND） |
| 串口连不上、报 `device reports readiness to read but returned no data` | USB-TTL 被车拖动松了 / 动力电把 USB 拉垮 / 被别的进程占用 | `pgrep -af python3`（**别据此判断"还有残留"**，它可能匹配到自己） | 换线换口 + 扎带固定；动力电与 USB 供电分开；`ps -eo pid,args \| grep python3 \| grep -v grep` 后 `kill <PID>` |
| 上电就自己跑一串动作 | 固件里测试动作没注释 / `INIT_STEPS` 被执行了两遍 | 固件 `RUN_DEBUG_SEQ` 类宏；日志里 `[init]` 出现两次 | 固件里关测试宏；臂已在起始位时加 `--no-init` |
| 上电初始化顶死限位 | `INIT_STEPS` 是**相对行程**，臂已在起始位又走一遍 | 日志 `[init] 上电初始化 3 步` | 加 `--no-init`；真顶死了先断电再手摇回摆放位 |
| 动一下就报 `PackError('32位越界…')` | 某步脉冲填成 0 或负数（最常见是把"抬高量/下放量"填反） | 日志里 `!! 第 N 步 … 的脉冲不合法（= -1800，必须 > 0）→ 跳过这一步` | `_run_rack` 已自动跳过该步并告警 → 按 N 回参数区改；⚠️ **绝不能把负脉冲直接下发** |

### 6.2 动作组"打架"

| 症状 | 最可能原因 | 查哪里 | 怎么修 |
|---|---|---|---|
| **"没到位就下一步"**（伸缩还在飞，龙门/夹爪就动） | TTL 估时偏短（老公式只算匀速段）/ 速度提上去了但斜率没跟 | 日志 `等到位 ≈ X.XXs（匀速 a + 加减速 b + 轴裕量 c + 余量 d）` 与实际录像对比 | `TTL_ACC_RPM_PER_S` 回 **400**；或 `TTL_EXTRA_S["gantry"]` 回 **0.5**（§4.3） |
| **"长时间停止延时"**（三种，必须分清） | ① 跑图**段间在等你回车**（`pause()`）；② **ACK 超时**（白等满 10s）；③ 固件**到位判据慢** | ①日志有 `按回车继续（q=退出）>`；②上一行 `!! ACK 超时 cmd=0x01（10.0s）`；③有 `⏱ 【…】花了 X.Xs` 但**没有**超时行 | ①加 `--auto`；②查串口/USB/固件是否忙；③属固件斜坡减速，非上位机可调 |
| 放完物料之后**没有后续动作** | 某步脉冲非法抛 `PackError` **打断整组**（历史现场：第 6 步 −1800） | 找 `PackError` / `脉冲不合法` 日志 | 见 §6.1 最后一行 |
| 高度越走越高 / 放完料回不到瞄准高度 | `RACK_LIFT_BACK` 的**高度账没配平**：①+UP ④−DOWN ⑥+CLEAR ⑨+BACK 之和必须 = 0 | 参数区注释里的"高度账"；`_back_steps()` 的方向判断 | `RACK_LIFT_BACK = DOWN − UP − CLEAR`（**允许为负 = 下放**）；`0` 时该步自动省略 |
| 转 base 时**把物料打飞** | 顺序错：缩着伸缩就转 base（缩回半径 ≈ 物料所在半径，正好扫到） | `RACK_STEPS` 里 ⑦`arm_out` 是否在 ⑧`base_left` **之前** | **必须先伸出伸缩、再转回 base**（参数区有大段注释，别再犯） |
| 点 1 却朝反方向转 | base 那两步是**相对脉冲**，隐含"此刻在 90° 作业位"的前提 | 日志 `第N步 转到 X 号位：base 目标角 = …°` | 已在 `_run_rack` 里改成**绝对角定位**（`goto_base_deg`）；软跟踪初值必须是 **0°**（初始化结束时 base 在正前方），写成 90° 会出现"`l` 不动、`h` 却转 90°" |

## 七、现场操作 checklist

### 7.1 到场地第一天（按顺序，别跳步）

**第 0 步 · 硬件**
1. STM32 上电前**架空 / 清空机构上方**（存在"盲升归顶"类初始化动作）；
2. 接线：USB-TTL → **PA9/PA10/GND**（交叉）；闭环电机 → **PC10/PC11**；相机插好、环形补光打开；
3. `ls /dev/ttyUSB*` 确认串口，统一用 **`/dev/stm32`**。

**第 1 步 · 固件**
4. Keil 打开对应工程 → **Rebuild（0 Error）** → **确认 `OBJ\*.hex` 时间戳是刚编的**再烧
   （烧旧 hex 会浪费几小时，是本项目最贵的坑）；
5. 上电应只做初始化 + 归位，然后**静待串口**（若自跑循环＝测试动作没注释）。

**第 2 步 · 上位机**
6. 部署到在用那台板子（`deploy_visualbot2.ps1`），远端 `py_compile` 通过；
7. `python3 -u check_env.py` —— 确认**在哪个目录跑、加载的哪份代码、档案从哪读、相机串口在不在**；
8. `python3 find_cam.py` 确认相机索引（必要时改 `CAM_INDEX`）。

**第 3 步 · 视觉与方向（先定方向，再调一切阈值）**
9. 开监控台 `monitor_ui.py … --port 8092` → 顶部【画面方向】四个按钮挨个点，
   选到"画面摆正、靶标是正圆不是椭圆"那一档（点一下即写回 `ring_calib.json`）；
10. `python3 -u exposure_tune.py` 按当前场景挑曝光档 → 回填 `CAM_EXPOSURE`；
11. 圆环：`ring_stream_ui.py --cam 0 --port 8091` → 自动估参 → 保存档案 → **跑三套回归**；
12. 颜色：`color_blob_stream.py --cam 0 --port 8090`（或彩色标靶台 `target_stream_ui.py --port 8091`）
    → 各色 ROI 自动标定 → **保存档案**。

**第 4 步 · 机械与标定（分步，别一上来全自动）**
13. 架空轮子 → 逐个手试行程（菜单 `m`）：`TELESCOPE` / `LIFT_UP` / `LIFT_DOWN` / `BASE_90` / 夹爪角度；
14. 打 **`v 30`** 静止抖动测试：3σ 抖动 > `AIM_TOL_PX` 就先治视觉，别急着调控制参数；
15. 打 **`c 200 800`** 重标 K（会真的动电机，先清场）→ 按提示抄回 `K_BASE`/`K_ARM`/`K_R_REF`；
16. 里程：`route_debug.py` 的比例法（发一段 → 量实测 → 它算比例 → 打印建议值）；
17. 先单步（`l → a → z → P → b → 0`），再一条龙 `A/B/C`，最后才把作业嵌进跑图。

### 7.2 每次改完参数

1. 确认改的是**哪一层**、名字**是否在白名单**（§1.1 / §1.2）；
2. `py_compile` 或直接重跑；
3. **重启进程**（只有瞄准的少数项能 `k` 热改）；
4. 打 **`k`** 核对**实际生效值**；
5. 架空/清场后再上地；
6. **`git commit`**（`git diff` 是唯一可信的"改了哪一行"）。

### 7.3 收工前

1. 把菜单 `p` 打印的动作组、`k` 打印的生效参数**抄回参数区**（demo 退出时也会自动打印一遍）；
2. 两个 JSON 档案确认**已点"保存档案"**；
3. 停所有推流/调参台进程 → `ps -eo pid,args | grep python3 | grep -v grep` 确认干净；
4. 若在**板上**改过参数 → `..\deploy_pi\pull_from_rdk.ps1 -RemoteDir /root/VisualBot3` 拉回本地；
5. 归档当天的实测记录（偏移/耗时/卡在哪），并在 `git commit` message 里写清"改了什么、为什么"。

| 端口 | 用途 | 启动命令（板上 `cd /root/VisualBot3`） | 备注 |
|---|---|---|---|
| **8090** | **物料颜色**调参台 | `python3 color_blob_stream.py --cam 0 --port 8090` | 6 色阈值 + ROI 自动标定；存 `color_profile.json` |
| **8091** | **圆环**调参台 | `python3 ring_stream_ui.py --cam 0 --port 8091` | 全部 CALIB 滑条 + 诊断面板；存 `ring_calib.json` |

  （Jetson→`high`、**RDK X5→`rdk`**），且档案同名不同内容。
- 收尾：`kill $(cat /tmp/ring_stream_ui.pid)` 或 `bash kill_rsui.sh`；不要用 `pkill -f`（会杀自己）。

## § 调参心法

1. **先确认"这个参数会不会生效"，再动手改。** 四层地图 + `AIM_KEYS`/`VISION_KEYS` 白名单是全部前提；
   `getattr(别处模块, 名字, 兜底)` 只在那个模块真有那个键时才生效 —— 静默回退是本项目最常见的"改了没反应"。
2. **一次只动一个变量，并且先量再调。** 静止抖动打 `v`、方向打 `c`、里程用比例法、
   估时用秒表量总时间反推斜率 —— 有工具能**直接量出来**的事，绝不靠现象猜（"方向反"和"超调"的现象不一样，
   但很多人会把它当同一回事）。
3. **两组等待永远分开想。** "机械到没到位"（`TTL_*`，在 `school_config`）与"画面稳没稳"（`AIM_SETTLE_S`/`AIM_WARMUP_SETTLE_S`，
   在白名单里）治的是不同的病；症状是"动作打架"就查前者，是"画面晃/方向反"就查后者。
4. **提速只提大动作，瞄准打死不提。** 底盘与 TTL 大行程可以提（并按 §4.3 备好回退开关），
   但 `AIM_VEL_*` 保持 40：56 脉冲只要 4ms，提速的收益是几毫秒，代价是丢步 + 余振 + 更瞄不准。
5. **调参是双向的，能退回去才算调好。** 每次提速/加限幅都要预先想好"出现什么症状就退回哪个值"；
   稳定压过速度 —— 赛规"静止 15s 判负"，但**没到位就下一步**丢掉的是整轮分数。
