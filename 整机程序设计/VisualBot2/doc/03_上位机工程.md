# 03 上位机工程

> **一句话概括**：上位机是跑在 RDK X5 上的 Python 3 + OpenCV 4.11（**无 GStreamer**）程序，经
> `/dev/stm32` 串口驱动 STM32 底盘与机械臂，有**跑图主程序 / 分步调试器 / 浏览器调参台**三种运行
> 形态；现场参数集中在 `grab_demo.py` 参数区，靠 `build_car()` 里的 `AIM_KEYS + VISION_KEYS` 循环
> **注入** `school_config` —— **不在这两个元组里的参数改了不生效**，这是本项目最容易踩的坑。

### 2.2 共享库 / 协议层（本地 `校赛\`，部署后复制进同一目录）

各文件职责（依据：各文件头部 docstring）：
`car.py` = 车与机械臂**动作函数库**（`fwd/base_left/arm_out/grip_close/pick_at/apply_step/replay/init_axes`…），
含 TTL 单轴"预计耗时"估算；`aim.py` = **瞄准闭环**，三阶段 `X1→Y→X2`（阶段 A 只用 base 收 x、阶段 B 只用

`RingVision`/`ColorVision`/`BlobTracker`/`FrameHub`（帧共享），自动合并 `ring_calib.json` 与
`color_profile.json`；`lower_api.py` = **串口协议层**（唯一的下位机入口）：10 字节定长帧
`0xFF+cmd+7B+0xFE`、大端、无校验，`MockLower` 支持无硬件跑全流程；`school_config.py` = **规则常量 + 参数
默认值仓库**：任务码解析、颜色映射、`PLACEMENT_MAP`、超时、瞄准/视觉参数默认值、TTL 估时；
`cam_rotate.py` = **画面方向唯一开关**（`none/ccw/cw/180`），优先级
`CALIB["rotate_ccw"] < ring_calib.json < 显式传参`；`qr_scan.py` = 侧装扫码：`decode_qr()` / `listen()`
（连续 N 帧一致才采纳）/ `scan_while_moving()`；`ledger.py` = 车载物料账本（物料编号 ↔ 物架 slot），用于
"取料顺序 ≠ 放置顺序"。

## 3. 三种运行形态（★最容易混）

| | 形态 A：跑图主程序 | 形态 B：分步调试器 | 形态 C：浏览器调参台 |
|---|---|---|---|
| 程序 | `route_main.py` | `grab_demo.py` / `place_demo.py` | `*_stream_ui.py` / `monitor_ui.py` |
| 交互 | 终端；**每段停下等回车**，`q` 退出 | 终端**交互命令菜单** | **浏览器**滑条/按钮，终端零窗口 |
| 谁动电机 | 底盘 + base + 机械臂（`*_IN_ROUTE=True` 时） | 全轴，**单步可控** | **完全不动电机** |
| 用在哪 | 联调、比赛 | 把某套动作一步一步试出来 | 调视觉阈值、看画面 |

### 3.1 形态 A：`route_main.py` 跑图（七段）

```bash
cd /root/VisualBot2 && python3 -u route_main.py --port /dev/stm32   # 分段，每段停下等回车
# 开关：--auto 一口气跑完 ｜ --start N 从第 N 段开始 ｜ --dry-run 不连车 ｜ --no-monitor 不开推流
```

七段定义见 `route_main.py` 的 `STAGES`（第 502–510 行）：

| 段 | 函数 | 内容 | 停顿时"要量的东西" |
|---|---|---|---|
| ① | `s1_out()` | 出启动区右移 `RIGHT_OUT`（非 auto 先 `car.pause()` 等确认场地清空） | 右移了多少 cm |
| ② | `s2_scan()` | **去扫码位路上**先 `base_cw(BASE_180, wait=False)`，再 `fwd(TO_SCAN)` 阻塞，"谁慢等谁"补时；到位读码、`base_ccw` 转回 | 前进距离、base 转 180° 后能否稳定读码 |
| ③ | `s3_material()` | 进原料区 `TO_MATERIAL` → `base_left(BASE_90)` → 按取料顺序在 1/2/3 号位间 `goto_cm` → 每处「瞄准→取料→放到对应物架」 | 进区距离、base 是否 90°、相邻号位 10cm |
| ④ | `s4_leave_material()` | 从**当前料位**直接前进 `TO_PROCESS − cur_cm`，不绕回 1 号位（出区后绝对位置与老流程一致） | 前进距离 |
| ⑤ | `s5_spin()` | 原地自旋 `SPIN_DEG`（顺时针） | 实际转了多少度 |
| ⑥ | `s6_process()` | 进加工区 `ENTER_PROCESS` → `base_left(BASE_90)` → 每靶位调 `place_demo.run_one()`（瞄→归零→夹料→回放→放置→**回零**） | 进区距离、base 是否 90° |
| ⑦ | `s7_finish()` | 前进 `TO_FINISH` → 右移 `FINISH_RIGHT` → `right(31)`、`fwd(17)` → 停车 | 前进/右移距离 |

默认每段停下等回车并**加粗打印"要量的东西"**（第 620 行）—— 车主反馈过"右移出启动区后长时间停止"，
其实就是这里在等回车；`--auto` 下 `car.pause()` 全跳过，但**开跑前那一次强制等回车保留**（第 604–605
行）。**扫码段必须开着推流**（不得加 `--no-monitor`）：`route_main` 不自己开扫码相机，而是问推流页面的
`/state` 要解码结果（连续 3 帧一致才采纳，见 `scan_from_monitor()` 第 155–181 行）。上电初始化
`INIT_STEPS` 是**相对行程**，臂已在起始位时**必须**加 `--no-init`，否则继续往同方向走 → 顶死限位。

### 3.2 形态 B：`grab_demo.py` / `place_demo.py` 分步调试器

```bash
python3 -u grab_demo.py  --port /dev/stm32 --color red   # 原料区（--color red/green/blue）；--dry-run 不连车
python3 -u place_demo.py --port /dev/stm32               # 加工区（首次上电带初始化）；--no-init 之后每次
```

`grab_demo.py` 菜单（`MENU` 第 984–997 行）：`h`/`l` 归位（base→0°）/进作业姿态（base→90° 左侧工作位）；
`a` 只瞄准并记账偏移；`g` 取料一遍（瞄准 + `PICK_STEPS`）；`1`/`2`/`3` 放到物架对应号位（先 `rack_zero()`
归零再跑 `RACK_STEPS[n]`，可加角度如 `1 60`）；`A`/`B`/`C` 一条龙（瞄→夹→放 1/2/3）；`n` 切换当前动作组
（`PICK`/`RACK1`/`RACK2`/`RACK3`）；`s` 单步跑当前组（回车=执行，`s`=跳过，`r`=重跑上一步，`q`=退出）；
`p` 打印当前组（**可直接粘回参数区**）；`e N [脉冲] [速度]`/`i N 名称 [脉冲]`/`d N` 改/插入/删除第 N 步；
`m` 手动发单个动作（`b`base / `l`龙门 / `a`伸缩 / `g`夹爪 / `w`等待）；`v [帧数]` 静止抖动测试（**瞄准摇摆
先测这个**，不动电机）；`c [base脉冲] [arm脉冲]` 重测 K 值/查耦合/验方向（推荐 `c 200 800`，**会动电机**）；
`k` / `k 名字 值` 看瞄准参数 / 现场改（如 `k COLOR_EMA 0.25`，改的是 `SC` 上的值，不用重部署）；`x` 停车；
`q` 退出（退出时打印全部四组动作组代码，可抄回参数区）。

`place_demo.py` 菜单（`MENU` 第 237–247 行）：`h`/`l` 归位·作业位；`a` 只瞄准标靶（**记住本次 off**）；
`z` 归零（把 off 还回去 → 得到"夹料的确定起点"）；`b` 回放（把 off 正着补回来 → 回到靶心）；`n` 换靶位
1/2/3；`P` 从物架夹料（只夹）；`0` 只放置；`A`/`B`/`C` 一条龙（瞄→归零→夹→回放→放）；`v`/`c` 抖动测试·
K 值标定；`k`/`m`/`p` 看参数·手动动作·打印动作组；`q` 退出。**完整手动顺序 `l → a → z → P → b → 0`**
（第 246 行）。顺序不能颠倒：瞄准会动**伸缩**（相对位移），必须"先瞄 → 归零 → 夹料 → 把 off 补回来"，
夹料完才能精确回到靶心（第 18–24 行）。菜单里 `A/B/C` 与 `a` 的区分靠 `p[0]` **原样**判断（`c` 已
`lower()`，大写 `A` 会变成 `a` 被瞄准分支抢走）—— 2026-09-17 修掉的老 bug，改动菜单时别退化。

## 4. ★★参数注入机制（最容易踩的坑）

`grab_demo.py` 顶部"参数区"（约第 60–421 行）里，只有**名字出现在 `AIM_KEYS` 或 `VISION_KEYS` 两个元组
里**的变量，才会被注入 `school_config`（`grab_demo.py` 第 676–697 行；注释原话："参数注入必须在
`use_camera()` **之前**"—— `ColorVision` 在 `use_camera()` 里创建，那一刻就读 `COLOR_EMA` 等滤波参数）：

```python
def build_car(a):
    SC.K_PX2STEP_BASE = K_BASE
    SC.K_PX2STEP_ARM = K_ARM
    for _k in AIM_KEYS + VISION_KEYS:
        setattr(SC, _k, globals()[_k])
```

`route_main.py` 在 `main()` 里用**同一套注入**（第 556–566 行）：

```python
import grab_demo as G
SC.K_PX2STEP_BASE = G.K_BASE
SC.K_PX2STEP_ARM  = G.K_ARM
for _k in G.AIM_KEYS + G.VISION_KEYS:
    _v = getattr(G, _k, None)
    if _v is not None:
        setattr(SC, _k, _v)
```

⇒ **`grab_demo.py` 参数区是全部瞄准/滤波参数的唯一权威来源**；`route_main` 只把它抄过来，不在自己文件
里另写一份（第 546–550 行注释说明了为什么：那些值是现场一点点标出来的，再写一份必然走样）。

## 7. `sys.path` 约定（为什么要倒序插入）

`grab_demo.py` / `route_main.py` / `route_car.py` / `route_debug.py` / `place_demo.py` /
`target_stream_ui.py` 顶部都有一段**一模一样**的代码（原文见 `route_main.py` 第 33–46 行）：

```python
HERE = os.path.dirname(os.path.abspath(__file__))
# ★★sys.path 顺序至关重要（2026-09-18 的大坑）：共享模块会把**老工程 `/root/VisualBot`**
#   也塞进 sys.path，而 `/root/VisualBot/校赛/` 下有**同名的旧版 aim.py / car.py / vision.py**。
#   原来的顺序插入（`insert(0, …)` 逐个加）会让**后插的排最前**，`/root/VisualBot`
#   反超成本目录之前 → `import aim` 命中旧版 → 三阶段瞄准/软化/arm 阻尼/K 全部失效。
#   → 倒序插入 + 先清掉重插，保证本项目自己的目录最终排最前。
for _p in ("/root/VisualBot", "/root/VisualBot2", HERE):
    if not _p or not os.path.isdir(_p):
        continue
    while _p in sys.path:
        sys.path.remove(_p)
    sys.path.insert(0, _p)
```

**三个机制**：`while _p in sys.path: remove(_p)` 先**清掉已有条目**（否则重复 `insert` 会留多份）；因为
每次 `insert(0, …)` 都排到最前，所以按 `("/root/VisualBot", "/root/VisualBot2", HERE)` 顺序处理后，
**后插的 `HERE` 最终排最前**（`HERE, /root/VisualBot2, /root/VisualBot`）⇒ `import aim`/`car`/`vision`
一定命中**本目录**版本。

**为什么这问题很阴险**（`route_car.py` 第 28–36 行原话）：共享模块会把老工程 `/root/VisualBot` 也塞进
`sys.path`，而 `/root/VisualBot/校赛/` 下有**同名的旧版** `aim.py` / `car.py` / `vision.py`；原来这里是
`for p in (HERE, …): insert(0, p)` —— 顺序插入，**后插的排最前**，于是 `/root/VisualBot` 反超到
`sys.path[0]` → `import aim` 命中**旧版** → 三阶段瞄准等新改动**全部静默失效**。车主发现"三阶段没整合
进去"就是它。实测证据：`>>> aim = /root/VisualBot/校赛/aim.py`。**验证方法**：`check_env.py` 的 ② 段会
打印每个关键模块**实际加载自哪个文件**（形如 `car  /root/VisualBot2/car.py`）。

> ⚠️ **待确认**：元组里硬编码的是 `/root/VisualBot2`，**不是 `/root/VisualBot3`**。若最终部署目录改为
> `/root/VisualBot3`，这**六处**元组都要同步改（否则本目录仍会被 `/root/VisualBot2` 压住，或更糟 ——
> 命中 VisualBot2 的旧代码）。改法是照抄 `HERE` 的处理，或干脆只留 `HERE`。

## 8. 模块循环 import 问题（★改动时别把 import 挪到顶层）

**环长什么样**：`grab_demo.py` 顶层 `import route_main as RM`（第 57 行，为了取 `BASE_90`/`TTL_VEL`）；
`place_demo.py` 顶层 `from grab_demo import (...)`（第 93–97 行）⇒ **`place_demo → grab_demo →
route_main` 成环**。因此成环那一侧的 `import` **必须写在函数体内**，延迟到调用时才执行：

```python
# route_main.py s3_material() 第 304–313 行
# ★必须在**函数内** import：grab_demo 顶层有 `import route_main as RM`，
#   顶层互相 import 会成环 → 这里延迟到调用时才导入就没事。
if PICK_IN_ROUTE:
    from grab_demo import (aim_and_track, rack_zero, _run_rack, PICK_STEPS,
                           RACK_STEPS, RACK_HOME_BEFORE, RACK_WORK_DEG,
                           merge_zero_into_steps)

# route_main.py s6_process() 第 428–436 行
# ★必须在**函数内** import：place_demo 顶层 import 了 grab_demo，而 grab_demo
#   顶层又 `import route_main as RM` → 顶层互相 import 会成环，延迟到这里就没事。
if PLACE_IN_ROUTE:
    from place_demo import run_one, TARGET_COLOR, RACK_WORK_DEG as _PLACE_WORK
```

`route_main.main()` 里的 `import grab_demo as G`（第 556 行）同样是函数内 import，理由见第 549–550 行
注释：**"`grab_demo` 顶层 import 了 `route_main`，但那是模块级、此时 `route_main` 早已加载完，不会
成环"** —— 也就是说 `import` 写在函数里就一定安全（执行到那一行时 `route_main` 已在 `sys.modules`
里），写在模块顶层才会成环。**接手人注意**：把这几个 `import` 从函数里挪到文件顶部 = **启动即失败**
（`ImportError` 或 `partially initialized module`）；看到
`cannot import name ... from partially initialized module` 一类报错，先回来查这三处。

## 11. 接手人第一天该做的事

1. **确认板子在不在、跑哪个目录**：`ssh rdk "hostname; ls -d /root/VisualBot* ; pgrep -af python3"`
   → 判据：能 SSH 进去；看清三个 `VisualBot*` 哪些存在、哪个有进程在跑。IP 变了先改 `~/.ssh/config`
   的 `Host rdk / HostName`（或跑 `find_rdk.ps1`）。
2. **跑环境自检**（最重要的单步）：`ssh rdk "cd <实际目录> && python3 -u check_env.py"` → 判据：② 段里
   `car`/`aim`/`vision` **都指向本目录**；④ 段有 `/dev/video0`；⑤ 段串口打开测试 ✓。若 ② 指向老工程 →
   立刻检查 §7 的 `sys.path` 元组。
3. **对着 `check_env.py` ③ 段确认标定档案** → 判据：`color_profile.json`/`ring_calib.json` 命中的是
   **当前部署目录下**那份，mtime 与最近一次现场调参吻合。
4. **只读比对一次**：`powershell -File 整机程序设计\deploy_pi\pull_from_rdk.ps1 -RemoteDir <实际目录>
   -LocalSchool "整机程序设计\VisualBot2"` → 判据：知道"板子上与本地不同的文件"是哪些。**这一步绝对
   不能跳过。**
5. **把现场改动收进本地并提交**（若第 4 步有差异）：加 `-Apply` 拉回 → `git diff` → 按 `命名规范.md` §3
   写 commit → `git push` → 判据：`git status` 干净、本地与板子一致。
6. **不连车先验流程**：`python3 -u route_main.py --dry-run` → 判据：七段依次跑完、每段打印"要量的东西"、
   无异常退出。
7. **开推流看画面**：`python3 -u monitor_ui.py --work-cam 0 --scan-cam 1 --perf rdk --port 8092`，浏览器
   开 `http://<当前IP>:8092/` → 判据：左路有画面（圆环/十字标注）、右路有画面（二维码框）。**先
   `pgrep -af python3` 确认没有别人占着 video0/video2。**
8. **读三处信息量最大的源码注释**：`grab_demo.py` 第 60–421 行（参数区 + 两个 KEYS 元组）、
   `place_demo.py` 第 10–56 行（工序顺序与"为什么先瞄后夹"）、`route_main.py` 第 502–510 行（七段定义）
   → 判据：能回答"要改瞄准分段限幅，改哪个文件的哪一行、为什么改别处不生效"。
9. **做一次"参数注入"验证实验**（建立肌肉记忆）：在 `grab_demo.py` 里敲 `k` 记下 `AIM_LIMIT_STAGES` 的
   值，再确认它在 `AIM_KEYS` 里 → 判据：能说清"参数区 → `AIM_KEYS`/`VISION_KEYS` → `setattr(SC, …)` →
   运行时生效"这条链。
10. **记住三条硬规矩**：① 部署前**必须先 pull 对比**，绝不用 `-Force` 覆盖现场调过的参数；② 改参数先
    确认它在不在 `AIM_KEYS`/`VISION_KEYS` 里；③ 三个程序之间的 `import` **不许挪到文件顶部**。
